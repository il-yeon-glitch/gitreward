# Git Reward 기획서

> 2026 교내 해커톤 / 팀 YDAA
> 이 문서는 프로젝트의 계약서다. 여기 정의된 데이터 형태와 파일 구조는 임의로 바꾸지 않는다.

---

## 1. 한 줄 정의

깃허브 기여 기록을 RPG 캐릭터 카드로 바꿔 디스코드에 보여주는 서비스.

## 2. 왜 만드는가

팀 과제에서 누가 무엇을 얼마나 했는지 잘 드러나지 않는다. GitHub에 기록이 남아 있어도 통계 메뉴를 직접 찾아 들어가야 하고, 표와 그래프뿐이라 다시 열어볼 이유가 없다.

Git Reward는 그 기록을 캐릭터 능력치로 바꿔, 팀이 하루 종일 켜두는 디스코드로 먼저 보낸다. 기록을 **보여주는** 데서 그치지 않고 **남기고 싶게** 만드는 것이 목적이다.

---

## 3. 데이터 흐름

```
저장소 주소 입력
   → GitHub API로 참여자별 기여 기록 수집
   → 능력치로 환산
   → 카드 이미지 생성
   → 디스코드 / 웹으로 출력
```

**입력은 저장소 주소 하나로 고정한다.** GitHub 아이디로 조회하는 방식은 API 경로가 달라 코드를 두 벌 짜야 하므로 이번 범위에서 제외한다.

---

## 4. 데이터 형태 (변경 금지)

파일 사이에 오가는 데이터는 아래 형태를 따른다. **키 이름과 타입을 바꾸지 않는다.**

```python
{
    "login":        str,   # GitHub 아이디
    "avatar":       str,   # 프로필 이미지 URL
    "commits":      int,   # 커밋 횟수
    "additions":    int,   # 추가한 줄 수
    "deletions":    int,   # 삭제한 줄 수
    "active_weeks": int,   # 활동한 주 수
}
```

이 형태가 고정되어 있어야 각자 다른 파일을 동시에 작업할 수 있다. 바꿔야 할 일이 생기면 혼자 고치지 말고 팀에 먼저 알린다.

> **참고** — GitHub에는 "수정"이라는 수치가 없다. 한 줄을 고치면 `삭제 1 + 추가 1`로 계산된다.

## 5. 파일 구조

| 파일 | 입력 | 출력 |
|---|---|---|
| `config.py` | — | 능력치 이름·계수, 색상 등 설정값 |
| `fetch.py` | 저장소 주소 | 위 딕셔너리 리스트 (JSON 저장) |
| `stats.py` | 딕셔너리 | 레벨 + 능력치(HP/ATK/DEF) + 경험치 |
| `card.py` | 능력치 | PNG 이미지 |
| `bot.py` | 디스코드 명령 | 채널에 카드 전송 |
| `web.py` | 저장된 JSON | 순위 페이지 |

```
gitreward/
├── .env               # 토큰 (절대 커밋 금지)
├── .env.example       # 빈 껍데기 (커밋함)
├── config.py
├── fetch.py
├── stats.py
├── card.py
├── bot.py
├── web.py
├── assets/            # 카드 배경, 폰트
├── cache/             # 수집한 JSON
└── docs/
    ├── 기획.md
    └── 함정.md
```

**한 파일은 한 사람만 수정한다.** 이것만 지키면 충돌이 원천적으로 발생하지 않는다.

## 6. 레벨 · 능력치 환산

**2026-08-21 기획 변경.** 기존에는 커밋 횟수·추가한 줄 수·삭제한 줄 수·활동 주 수가 각각 하나의 능력치(ATK/DEF/AGI/STA)로 1:1 환산됐다. 이 방식을 폐기하고 아래 구조로 바꾼다. 바꿔야 할 일이 또 생기면 혼자 고치지 말고 팀에 먼저 알린다.

### 6-1. 기여 기록 → 레벨

커밋 횟수, 추가한 줄 수, 삭제한 줄 수를 **하나로 합쳐 레벨**로 환산한다. 능력치별로 나눠 담지 않는다.

- 구체적인 환산 공식(계수, `LEVEL_DIVISOR` 같은 값)은 **미정이다.** 여러 저장소로 표본을 넣어보며 레벨이 적당한 구간에 떨어지도록 다시 맞춰야 한다. (기존 "레벨 20~50" 목표 구간을 그대로 쓸지도 재검토 대상)
- `active_weeks`(활동 주 수)를 이 공식에 포함할지는 **미정이다.** 게임 시스템을 담당하는 팀원이 정확한 레벨링을 확정할 때 함께 정한다. 그 전까지는 사용하지 않는 것으로 두고 작업한다.
- 공식이 확정되기 전까지도 수치는 **`config.py`에 모아둔다.** 다른 파일에 직접 적지 않는다.

### 6-2. 레벨업 → 능력치 성장

커밋 횟수·추가한 줄 수·삭제한 줄 수가 능력치를 직접 만들지 않는다. 대신 **레벨이 오를 때마다** 능력치가 성장한다.

새 능력치는 **HP(체력) · ATK(공격력) · DEF(방어력)** 세 가지다. 기존 AGI·STA는 없어진다.

레벨이 1 오르면:

1. 체력 · 공격력 · 방어력이 **기본으로 각각 +1**
2. 그중 **사용자가 선택한 능력치 하나에 +1을 추가로** 더 준다

즉 선택한 능력치는 레벨업당 +2, 나머지 둘은 +1씩 오른다. 선택을 어떻게 입력받을지(디스코드 명령 인자, 버튼 등)는 아직 정하지 않았다 — 게임 시스템을 담당하는 팀원이 확정한다.

### 6-3. 레벨업 필요 경험치

레벨이 오를수록 다음 레벨까지 필요한 경험치가 **조금씩 늘어난다.** 구체적인 증가 폭·공식은 게임 시스템을 담당하는 팀원이 확정한다.

## 7. 기술 스택

| 용도 | 사용 |
|---|---|
| 데이터 수집 | Python, requests |
| 이미지 생성 | Pillow |
| 디스코드 봇 | discord.py |
| 웹 | Flask |
| 저장 | JSON 파일 (기여 기록·카드 캐시) + SQLite (로그인/스텟 배분, 8번 참고) |

**기존에는 데이터베이스를 쓰지 않았다.** 저장할 데이터가 저장소당 참여자 몇 명 수준이라, 파일 하나를 통째로 읽는 편이 더 빠르고 실수도 적었기 때문이다. 이 원칙은 기여 기록·카드 캐시에는 그대로 유지한다. 다만 로그인/스텟 배분처럼 사용자별로 계속 쌓이고 수정되는 데이터는 **SQLite**로 저장한다 (2026-08-21 결정, 8번 참고). `sqlite3`는 파이썬 표준 라이브러리라 별도 설치가 필요 없다.

## 8. 범위

### 이번에 만드는 것

1. 저장소 주소로 참여자별 기여 기록 수집
2. 능력치·레벨 환산
3. 카드 이미지 자동 생성
4. 디스코드 슬래시 명령으로 카드 조회
5. 웹에서 카드 순위 나열

### 확장 예정

- **카드 결투** — 카드 두 장을 나란히 놓는 레이아웃까지 준비하고, 승패 규칙은 이후 확정
- 주간 자동 알림
- GitHub 아이디 단위 조회

### 로그인 / 데이터베이스 (2026-08-21 범위 추가)

원래 "하지 않는 것"에 있었지만, 그건 해커톤 전에 집에서 뼈대만 미리 만들 때 범위를 줄이려고 넣어둔 항목이었다. 이제 실제로 필요해져서 범위에 넣는다.

- **왜:** 스텟 배분(레벨업 포인트)을 아무나 남의 저장소·카드에 대고 조작할 수 있으면 안 된다. 요청한 사람이 그 카드의 진짜 주인인지 확인할 방법이 필요하다.
- **DB는 SQLite로 확정** (2026-08-21). 로그인 방식(어떤 인증을 쓸지)은 아직 미정 — 담당 팀원이 확정한다.
- 새 파일(`db.py` 등)이 필요해질 수 있는데, **파일 구조 변경은 팀에 먼저 알린 뒤 이 문서(5번)에 반영한다.** 임의로 만들지 않는다.

### 하지 않는 것

시간을 가장 많이 잡아먹으면서 결과물에 기여하지 않는 항목들이다.(정말 필요하면 사용할 예정)

- 실시간 웹훅 (수동 갱신만)
- 던전 등 게임 시스템 — **2026-08-21:** 아이템 요소는 삭제되고, 특정 스테이지·조건을 달성하면 **수집용 카드**를 발급하는 방식으로 바뀌었다. 이 게임 자체는 여전히 이 프로젝트(Git Reward) 범위 밖이며 다른 팀원이 담당한다.
  > ⚠️ 여기서 말하는 "수집용 카드"는 이 문서의 **능력치 카드**(GitHub 기여 기록을 `card.py`로 그린 PNG, 4번 데이터가 근거)와 **다른 것**이다. 헷갈리지 않게 코드·대화에서 구분해서 부른다.
- 여러 저장소 동시 처리
- 서버 배포 (로컬 실행으로 시연)
- 테스트 코드

## 9. 토큰 관리

| 항목 | 방식 |
|---|---|
| GitHub 토큰 | **각자 발급** (github.com/settings/tokens, 권한 체크 없이) |
| 디스코드 봇 토큰 | **담당자 한 명만** 보유 |
| 서버 ID | 공유 가능 (비밀 아님) |

- 디스코드 봇 토큰은 **동시에 한 사람만** 사용할 수 있다. 두 명이 같은 토큰으로 봇을 켜면 응답이 중복되거나 충돌한다.
- `.env` 파일을 카톡·디스코드로 주고받지 않는다. 채팅 기록에 토큰이 남는다.
- `.gitignore`에 `.env`를 반드시 넣는다. 커밋되면 GitHub이 감지해 토큰을 즉시 무효화한다.

## 10. 작업 원칙

1. **한 번에 한 파일씩.** 결과물이 눈에 보이는 것을 확인하고 다음으로 넘어간다.
2. **동작하는 코드는 건드리지 않는다.** 리팩터링은 대회가 끝난 뒤에.
3. **막힌 것은 `docs/함정.md`에 적는다.** 겪은 것만 적는다. 이 기록이 그대로 발표 자료의 트러블슈팅이 된다.
4. **작업 시작 전 `git pull`.**
